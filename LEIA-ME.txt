  DESCOMPLICA ENEM — SISTEMA AUTOMATIZADO
════════════════════════════════════════════

FLUXO COMPLETO:
  Aluno compra na Cakto
       ↓
  Cakto dispara webhook
       ↓
  Vercel cria login (email + senha)
       ↓
  Resend envia email bonito com as credenciais
       ↓
  Aluno entra com email + senha em acesso.html
       ↓
  Aulas e Arena desbloqueadas

────────────────────────────────────────────
PASSO 1 — SUPABASE (banco de dados gratuito)
────────────────────────────────────────────
1. Acesse: supabase.com → crie conta e projeto
2. Vá em SQL Editor → cole o conteúdo de supabase.sql → Execute
   (se a tabela "usuarios" já existia de antes, esse mesmo arquivo
   também adiciona as colunas novas de bloqueio por tentativas —
   pode rodar de novo sem problema, ele ignora o que já existe)
3. Vá em Settings > API:
   - Copie "Project URL"          → SUPABASE_URL
   - Copie "service_role" key     → SUPABASE_SERVICE_KEY
   (NUNCA use a anon key nas functions)

────────────────────────────────────────────
PASSO 2 — RESEND (email gratuito, 3000/mês)
────────────────────────────────────────────
1. Acesse: resend.com → crie conta gratuita
2. Adicione e verifique seu domínio (ou use @resend.dev para testes)
3. Vá em API Keys → Create API Key → copie → RESEND_API_KEY
4. Em EMAIL_FROM use: Descomplica ENEM <noreply@seudominio.com>

────────────────────────────────────────────
PASSO 3 — VERCEL (hospedagem gratuita)
────────────────────────────────────────────
1. Acesse: vercel.com → Add New → Project
2. Importe o repositório do GitHub (bernardopalacine/Descomplica-Enem)
   (a Vercel detecta sozinha o vercel.json e a pasta api/ — não precisa
   configurar build command nem output directory manualmente)
3. Antes de clicar em Deploy (ou depois, em Project Settings >
   Environment Variables), adicione:

   SUPABASE_URL          = https://xxxx.supabase.co
   SUPABASE_SERVICE_KEY  = eyJ... (service_role)
   RESEND_API_KEY        = re_...
   EMAIL_FROM            = Descomplica ENEM <noreply@seudominio.com>
   EMAIL_SUPORTE         = seu@email.com
   SITE_URL              = https://SEU-PROJETO.vercel.app (ou seu domínio)
   CAKTO_SECRET          = (veja passo 4 — IMPORTANTE, sem isso o webhook
                             fica desligado por segurança)
   SESSION_SECRET         = (opcional, mas recomendado — veja abaixo)

4. Depois do primeiro deploy, anote a URL do seu site:
   https://SEU-PROJETO.vercel.app

SESSION_SECRET (opcional): usado para assinar o cookie de login.
Se você não configurar, o sistema gera um valor a partir da sua
SUPABASE_SERVICE_KEY automaticamente — funciona sem esse passo, mas
o ideal é gerar uma string aleatória longa só para isso (qualquer
gerenciador de senhas serve) e colar aqui, separado da chave do banco.

────────────────────────────────────────────
PASSO 4 — CAKTO (webhook automático)
────────────────────────────────────────────
Sem um secret, qualquer pessoa que descobrisse a URL do webhook
poderia forjar uma "compra aprovada" para qualquer email e ganhar
acesso de graça. Por isso o api/webhook.js EXIGE um secret — sem ele,
ele recusa a requisição (erro 500) em vez de aceitar tudo.

1. Invente um secret forte (ex.: gere uma senha aleatória longa em
   um gerenciador de senhas — não precisa ser o que a Cakto sugerir).
2. Cole esse secret em VERCEL > Project Settings > Environment
   Variables > CAKTO_SECRET
3. Painel Cakto → Integrações → Webhooks → Adicionar webhook:
   URL:    https://SEU-PROJETO.vercel.app/webhook/cakto?secret=SEU_SECRET_AQUI
   Evento: Compra Aprovada
   (troque SEU_SECRET_AQUI pelo mesmo valor que você colocou em
   CAKTO_SECRET — é essa URL exata, com o "?secret=...", que garante
   que só a Cakto consegue liberar acesso)
4. Faça um novo deploy na Vercel para atualizar as variáveis
   (Deployments > ⋯ > Redeploy, ou dê um novo git push)

PRONTO! Zero trabalho manual a partir daqui.

ARQUIVOS DO PROJETO:
  public/
    index.html            → landing page (pública)
    acesso.html           → login email + senha (pública)
  content/
    aulas-completas.html  → aulas — NÃO fica em public/, só é entregue
                             pelo api/aulas.js depois de conferir login
    arena-enem.html       → Arena ENEM — mesma proteção, via api/arena.js
    Descomplica_Enem_Guia_Definitivo.pdf → ebook, mesma proteção, via
                             api/ebook.js
  api/
    webhook.js            → recebe Cakto, cria usuário, envia email
    login.js              → valida email + senha, cria a sessão
    recuperar.js          → gera nova senha e envia por email
    verificar-sessao.js   → confere se a sessão é válida (chamado pelo site)
    logout.js             → encerra a sessão
    aulas.js              → serve content/aulas-completas.html só se logado
    arena.js              → serve content/arena-enem.html só se logado
    ebook.js              → serve o PDF só se logado
    _lib/session.js       → assina/confere o cookie de sessão
    _lib/env.js           → limpa o valor de SITE_URL (usado só no corpo
                             dos emails, não em headers — ver nota abaixo)
  vercel.json             → configuração da Vercel (rotas, headers, e quais
                             arquivos de content/ cada function pode ler)
  package.json            → dependências
  supabase.sql            → SQL para criar/atualizar a tabela

PROTEÇÃO DE CONTEÚDO (Etapas 2 e 3): antes, aulas-completas.html,
arena-enem.html e o PDF do ebook ficavam em public/ — mesmo com a
"tela de login" na frente, dava pra ver/baixar o conteúdo inteiro com
"Ver código-fonte" ou acessando a URL direto, sem nunca ter logado.
Agora nenhum desses três arquivos existe mais como página/arquivo
público: api/aulas.js, api/arena.js e api/ebook.js conferem a sessão
(o mesmo cookie assinado do login) ANTES de mandar qualquer conteúdo
de volta. Sem sessão válida, a resposta é um redirecionamento pra
acesso.html — o conteúdo em si nunca chega em quem não está logado.

────────────────────────────────────────────
SE MUDAR UMA VARIÁVEL DE AMBIENTE E "NÃO FIZER EFEITO"
────────────────────────────────────────────
Já aconteceu de editar uma variável (ex.: SITE_URL) na Vercel, clicar
em "Redeploy" e o site continuar se comportando como se a mudança não
tivesse acontecido — inclusive dando erro 500 por causa de um valor
que já tinha sido corrigido no código. A causa foi cache de build da
própria Vercel reaproveitando um build antigo.

Se isso acontecer de novo: Deployments → ⋯ no deploy mais recente →
Redeploy → **desmarque "Use existing Build Cache"** antes de confirmar.
Isso força um build 100% do zero e resolve.

────────────────────────────────────────────
MIGRAÇÃO DE HOSPEDAGEM (Netlify → Vercel)
────────────────────────────────────────────
Este projeto já funcionou hospedado no Netlify (pasta netlify/ com as
mesmas functions). Migramos para a Vercel porque o plano gratuito do
Netlify tem só 300 minutos de build por mês (a Vercel tem 6000). A
lógica de negócio é idêntica nos dois — só o formato de entrada/saída
das functions muda entre as duas plataformas. O histórico do Netlify
continua disponível no histórico do Git, caso precise voltar algum dia.
